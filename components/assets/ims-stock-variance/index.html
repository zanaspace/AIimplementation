Stock-Take Variance Explainer

Before a store manager approves a stock count, the CICOD-AI rebuilds what should be on the shelf from the movement history: opening + received − issued − transferred ± returns. It compares that with what was counted, explains the gap, and flags suspicious patterns such as the same counter recording small losses at the same store week after week. Each row gets a risk badge and a recommendation. Bulk approval only covers rows that are fully explained and low risk.

Screen: Assets → Stock Taking Mang.Component: <ai-variance-explainer>Endpoint: /ims/explain-variance

2. How it works

Deterministic reconciliation does the arithmetic, an anomaly model scores the patterns, and an LLM only writes the explanation.

Capture

Each awaiting count (store, asset code, new and previous quantity, counter, date) is sent to /ims/explain-variance, together with the bin card, Receive Asset, Reserved & Pickup, Stock Transfer and Returns entries since the last approved count.

Protect

The gateway replaces staff names with internal IDs before the model call and puts them back afterwards. Asset data stays in-country on the sovereign model. Nothing leaves the tenant.

Reconcile

A rules engine computes opening + received − issued − transferred ± returns = expected, then counted − expected = unexplained. It spots approved pickups not yet posted and receipts still awaiting approval.

Score patterns

An anomaly model looks across 8 weeks of counts: repeated small losses by the same counter at the same store, counts with no second counter, duplicate open counts and blank quantities.

Explain

An LLM turns the numbers into a probable cause and a recommendation (Approve, Reject or Request recount), citing the movement records it used.

Confirm & learn

The approver decides. Following or overriding the CICOD-AI is recorded via /feedback. Recount outcomes are fed back each week so the model learns which flags were real.

Build steps

  1. Expose a movement query per asset code and store since the last approved count (bin card, receipts, pickups, transfers, returns, status changes).
  2. Build the reconciliation rules on the CICOD-AI Gateway, including "approved but not posted" and "received but awaiting approval".
  3. Train the anomaly model on 12 months of approved counts per counter and store. Start with rules (3+ small losses in 4 weeks) until there is enough history.
  4. Add the CICOD-AI Risk column and the drawer. Wire the events to the existing Approve and Reject actions and add a "Request recount" status.
  5. Run for 6 weeks in advisory mode and compare flags with recount results.
  6. Enable bulk approval of explained low-risk rows per store once flag precision is 85% or higher.

Controls

  • Feature flag ai.cicod.imsStockVariance in Assets Settings, on/off per tenant and per store.
  • Bulk approval is limited to fully explained rows at or below bulk-max-risk (default low). Value-at-risk above ₦50,000 is always high risk.
  • Every explanation, flag and decision is written to Settings → Audit (feature: CICOD-AI Stock Variance), including whether the approver followed the CICOD-AI.
  • Pattern flags about a counter are shown only to approvers above that counter, never to the counter or their peers.
