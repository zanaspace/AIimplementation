Registry Guardian & Forecast

Checks the Asset Registry cards for values that cannot be true, such as an average cost larger than the total value, and explains the likely root cause. It also finds duplicate units of measure and junk asset types and proposes a merge, and forecasts reorder points for the top consumables. A store officer or admin confirms every change.

2. How it works

Deterministic rules find the impossible values, an LLM writes the explanation and root cause, fuzzy matching clusters master data, and a time-series model sets reorder points.

Capture

The KPI values behind each card, the repository and category lists, the UOM and Asset Type tables, and 90 days of receipts and issues per store are sent to /ims/registry-check and /ims/reorder-forecast.

Protect

Only aggregates and master-data names leave IMS. User names in the audit trail are replaced with IDs, and the job runs on the sovereign model because asset values are Official data.

Check

Invariant rules: average ≤ total, available ≤ total when both count assets, status cards ≤ total, card counts = chart counts. Each failure gets an LLM explanation and the most likely root cause, drawn from a catalogue of known IMS defects.

Cluster

UOM and asset-type names are normalised (case, digits, plural, "@unit") and clustered. A spelling model catches "Intagible", and a test-data detector catches "Testt" and "testing".

Forecast

Exponential smoothing on daily issues per store and asset. Reorder point = daily use × lead time + safety stock at the chosen service level, with a 30-day order quantity.

Confirm & learn

The officer raises a fix, merges, edits the reorder point or dismisses. Each decision goes to /feedback. Dismissed rules are down-weighted for that tenant.

4. How to implement it in IMS

Mount (Asset Registry page)

<link rel="stylesheet" href="/ai/components/ims-registry-guardian.css">
<script src="/ai/shared/ai-gateway.js"></script>
<script src="/ai/components/ims-registry-guardian.js"></script>

<ai-registry-guardian source="#kpi-grid"
    repos-source="#repo-chart [data-repo]"
    cats-source="#cat-chart [data-cat]"
    store="Central Store"></ai-registry-guardian>

<script>
document.addEventListener('ai-registry-result', e =>
  e.detail.checks.forEach(c => kpiGrid.flag(c.id, c.severity)));
document.addEventListener('ai-master-merge', e =>
  settingsApi.queueMerge(e.detail));   // admin approves
document.addEventListener('ai-reorder-apply', e =>
  emailAlerts.setReorderPoint(e.detail));
</script>

Build steps

  1. Write the invariant rules against the same queries that feed the registry cards, and run them on every Sync.
  2. Build a root-cause catalogue from known defects (unit mismatch, unweighted averages, grouping by location type) for the LLM to cite.
  3. Add normalisation and clustering for UOM, Asset Type and Category names; queue merges as admin approvals that re-point existing assets.
  4. Train the per-store forecast on receipts and issues from Bin Card View; back-test on the last 90 days.
  5. Wire ai-reorder-apply to Settings → Email Alert so the Reorder alert uses the forecast point.
  6. Run in suggestion mode for 4 weeks and track how many flags are confirmed as real defects.

Controls

  • Feature flag ai.cicod.imsRegistryGuardian in IMS Settings, on/off per tenant.
  • Thresholds: flag "available ≫ total" above 10×; auto-suggest merges only above 0.85 similarity; forecast service level defaults to 95%.
  • Merges and renames never apply directly. They go to the IMS Approval queue, and every decision is written to Settings → Audit (feature: CICOD-AI Registry Guardian).
  • Users only see checks and forecasts for repositories their role can view.
