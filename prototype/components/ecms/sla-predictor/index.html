SLA Risk & Smart Escalation

Predicts which open tasks will breach their SLA before it happens. Every row in All Tasks gets a Breach risk badge, and the list can be sorted by risk. Clicking a badge opens a drawer that explains why (time in stage against the median, assignee load, approvals pending). It also proposes an early escalation to the line manager or alternate approver, with a drafted note. The officer edits and sends it.

Screen: ECMS → Tasks → All TasksComponent: <ai-sla-risk>Endpoint: /ecms/sla-risk

2. How it works

A survival-style gradient-boosted model scores every open task. Its top features are shown as plain reasons, and an LLM drafts the escalation note from them.

Capture

For each open task: queue, priority, SLA from the workflow, hours in the current stage, the assignee's open load from Resources, and approvals pending.

Protect

Only task metadata goes to the model. Titles are redacted of personal data (NIN, phone, email) before the note is drafted. Everything runs on the sovereign model.

Predict

A GBM survival model, trained on roughly 16k historical tasks and their stage timings, estimates the chance of breaching the SLA and the expected hours left.

Explain

Feature contributions become reasons: time in stage against the queue median, assignee load against the team median, days with the approver, and SLA used.

Propose

The target comes from the workflow's escalation chain. If an approval is stuck, it goes to the alternate approver. Otherwise it goes to the line manager. An LLM drafts the note.

Confirm & learn

The officer sends, edits, snoozes or dismisses the escalation. Each choice and the final outcome (breached or not) are logged via /feedback and used to retrain the model.

4. How to implement it in ECMS

Mount (All Tasks page)

<link rel="stylesheet" href="/ai/components/sla-predictor.css">
<script src="/ai/shared/ai-gateway.js"></script>
<script src="/ai/components/sla-predictor.js"></script>

<ai-sla-risk table="#tasks-table" drawer="#sla-drawer"
             horizon-hours="48"></ai-sla-risk>
<!-- each row: <tr data-task data-stage-hours …>
     with an empty <td data-sla-slot> -->
<div id="sla-drawer" hidden></div>

<script>
document.addEventListener('ai-sla-sort', e =>
  taskList.reorder(e.detail.order));
document.addEventListener('ai-sla-escalate', e =>
  taskApi.escalate(e.detail));   // host owns the task
</script>

Build steps

  1. Export stage history for all tasks: time entered and left each status, SLA per workflow, assignee, approvals.
  2. Train a survival GBM per tenant. Check calibration so "70%" really means 7 in 10 breach.
  3. Expose /ecms/sla-risk on the CICOD-AI Gateway (batch scoring and single-task explanation).
  4. Add the risk column and drawer to All Tasks. Wire ai-sla-escalate to the existing escalation API.
  5. Add the "CICOD-AI early escalation" option to the Workflow → Escalation step.
  6. Run in proposal mode for 4 weeks and compare breach rates against queues without it.

Controls

  • Feature flag ai.ecms.slaPredictor in ECMS Settings, on/off per tenant.
  • Risk thresholds (high ≥ 70%, medium ≥ 40%) and the horizon are set per queue. Auto-escalation stays off unless enabled in the Workflow Escalation step.
  • Every score shown, escalation sent, snooze and dismissal is written to the ECMS Audit Log (feature: CICOD-AI SLA Risk).
  • Escalation targets are limited to the workflow's approver chain and the assignee's line manager. Users only see risk for rows they can already see.
